# Security

Report vulnerabilities privately to the repository owner (do not open a public issue).

## Model
- **No server-side user data.** No database, accounts, stored conversations or recordings. Server state (rate limits, link codes, Calendar, task-list and mail & chat sessions, budget) is bounded, in memory, expiring, and cleared on restart.
- **Secrets only on the server.** AI keys (`GEMINI_`, `OPENAI_`, `ANTHROPIC_`, `OPENROUTER_API_KEY`) and OAuth client secrets (Google, Todoist, Notion, Slack) are read from the environment; `/api/status` exposes only provider ids and model names. `npm run lint` fails if client code references them or a built bundle contains `.env` values or Google/OpenAI/Anthropic/OpenRouter key patterns. `OLLAMA_BASE_URL` is server config only — the client can never choose an upstream URL.
- **Access control.** Every `/api/*` route except `/api/status` and `/api/session` requires a short-lived HMAC access token; production requires an operator access code. CORS uses an explicit allowlist and is not treated as authorization.
- **Cost controls.** Per-token rate limit, per-IP limit, global daily AI budget, payload limits (48 KB chat, ~760 KB voice), upstream timeouts.
- **OAuth.** Auth-code + PKCE (S256, Google), random single-use `state` bound to a pairing *and* to its provider, exact redirect URIs, single-use redemption bound to a poll secret, `access_type=online` for Google, scope check, no refresh tokens kept, task-list sessions capped at 12 h, revoke on disconnect (Google, Todoist, Notion, Slack). Tokens never appear in our URLs, logs, responses or client storage; the client holds only opaque in-memory session handles. Task-list reads return only id, title, due date, done flag and list name. Gmail uses `gmail.metadata` (headers only — the server never requests bodies) + `gmail.send`; the client and the AI see sender name, subject and date, never email addresses. Slack uses a user token with `search:read`, `chat:write`, `users:read`; reads return author name, channel and a ≤220-character preview of messages that mention the user.
- **AI output is untrusted.** Responses are schema-validated; unknown actions are dropped; the model sees opaque refs (`Q1`, `E1`) not IDs; external content is wrapped as data. Confirmation requirements are decided by trusted code. Proposals expire (5 min), are re-checked for staleness and cannot be replayed. Calendar creates are idempotent (deterministic event IDs) and verified by reading back; task completions are offered only after the user finishes the quest, need confirmation, are idempotent per proposal and verified by reading back.
- **Notes and channel posts** (Ask my notes, channel digest) are read on request only, minimized (Notion: titles + excerpts of at most three matching pages; Telegram: the latest posts of chats the bot is in, memory-only, ≤ 2 days), sent to the AI only for that one request, marked as untrusted data, and never stored on the server. The notes question travels in a POST body, never a URL.
- **GitHub tokens** are the user's own classic tokens, pasted only on the `/link` page; the server checks the `notifications` scope, keeps the token in memory ≤ 12 h, never returns or logs it, and can only list notification threads and mark one read after confirmation.
- **Telegram bot tokens** are the user's own: pasted only on the server-rendered `/link` page (POST body, CSP `form-action 'self'`, rate-limited), checked with `getMe`, held in server memory ≤ 12 h, never returned to the client, never logged; Telegram's API requires the token in the request path, so upstream URLs are never logged either. Bots with a webhook are refused. Received messages live in a bounded in-memory buffer (≤ 50, ≤ 3 days) and vanish on disconnect or restart. Business-mode replies honour Telegram's `can_reply` right and 24-hour window server-side.
- **Outgoing messages.** Email and Slack replies are proposals like any other action: exact text shown, confirm-first, idempotent per proposal, verified by reading back (Gmail `SENT` label, Slack echo). Recipients are decided by the server from the original message (a single bare address taken from `Reply-To`/`From`; header values are stripped of CR/LF so a crafted sender cannot inject headers). Replies containing profanity are rejected client-side and again server-side (`422`), so 18+ mode can never leak into mail or chat. Message content is wrapped as untrusted data in AI prompts (opaque refs `M1`–`M6`).
- **Assistant tasks** (catch-up, triage, suggestions, summaries, briefings) use the same minimized context and validated contract; AI reply suggestions are re-checked on the device (no profanity or forbidden content) and still need the exact confirmation to be sent. Background assists never show errors or fall back to invented text.
- **No tool can enable 18+ mode**; only the local consent dialog can. *Full 18+* widens only the Savage's comedic range; hard limits stay in the trusted system policy, Gemini's safety filters stay on (sexual content moves LOW → MEDIUM in Full 18+ only; nothing is BLOCK_NONE) and the never-allowed patterns are enforced locally in every mode.
- **Logging** is redacted: method, route, status, duration — never bodies, headers, tokens or query strings.

## Known limitations
Single-process ephemeral state means a restart drops active Calendar sessions and rate-limit counters; horizontal scaling would need a shared store, which is intentionally out of scope. The profanity detector is a heuristic, not a safety classifier; each AI provider’s own safety controls remain the primary content control (Gemini safety settings are explicitly kept on).
